# kortuli_bot — концепция

Документ для фазы проектирования. Фиксирует продукт, ограничения и уже принятые
решения, чтобы не пересматривать их заново на каждом шаге.

---

## 1. Проблема

В Тбилиси порядка 18 падел-площадок, и единой точки, где видно всю сетку свободных
слотов, не существует. У каждого клуба свой букинг: где-то SaaS, где-то WordPress,
где-то самописное приложение, где-то только телефон.

Вечерние слоты (19:00–22:00) разбираются за сутки-двое. Освобождаются рандомно,
через отмены. Узнать об отмене сейчас можно только вручную обновляя чужой сайт.

---

## 2. Что делает бот

**Основная фича — вотчер.** Пользователь подписывается на окно: дни недели +
диапазон времени + набор клубов. Бот опрашивает источники, ловит переход слота в
состояние «свободен» и пушит уведомление с диплинком на бронирование.

**Вторичная — разовый поиск.** Показать свободные слоты на ближайшие N дней.

Приоритет именно такой. Поиск — коммодити, человек и сам откроет два сайта.
Ценность в пуше про отмену.

## Чего бот НЕ делает (v1)

- **Не бронирует и не платит.** Только уведомление + диплинк, дальше человек сам.
  Причина: чужие аккаунты и платёжка — юридическая серая зона плюс поддержка,
  которую в одиночку не потянуть.
- Не хранит платёжные данные, не требует регистрации. Идентичность = telegram user id.
- Нет веб-морды.
- Нет матчмейкинга («найти партнёров на игру»). Соблазнительно, но это другой продукт
  с другой динамикой. Не смешивать.

---

## 3. Аудитория

Тбилисское падел-комьюнити: грузино-, русско- и англоязычные. Тексты бота — минимум
EN + RU. Имя «kortuli» само себя не объясняет, поэтому описание бота (`/setdescription`,
`/setabouttext`) несёт продуктовую нагрузку: первая строка отвечает на «что эта штука
делает».

---

## 4. Источники данных — главный риск проекта

**Это 90% работы.** Бот поверх данных — это вечер. Данные — это месяцы.

Известный ландшафт:

| Источник | Тип | Приоритет |
|---|---|---|
| Reservio (`padel-club2.reservio.com`) | SaaS, предсказуемая структура | **начинать отсюда** |
| BookingPress / WordPress (`tbilisipadel.com`) | admin-ajax эндпоинты | вторым |
| PadelHub, Padel Island (4 локации), PadelBade, GAMO | самописные | по одному, по мере надобности |
| `padelio.ge` | сам позиционируется как агрегатор с онлайн-оплатой | **разведать до старта**: конкурент или готовый единый источник |
| Часть площадок | только телефон | вне скоупа, данных нет |

Playtomic в Грузии не представлен — единого API не будет, это принципиально
N интеграций.

**Правило разведки:** прежде чем тащить headless-браузер, открыть DevTools. Под
React-виджетом почти всегда лежит чистый JSON-эндпоинт. Puppeteer на Raspberry Pi —
это боль и лишние сотни мегабайт RAM.

---

## 5. Уже принятые решения

Не пересматривать без новых вводных.

**Хостинг — Raspberry Pi.** Там уже крутится Telegram-ассистент, маржинальная
стоимость нулевая.

**НЕ Telegram Serverless.** Модель исполнения там чисто реактивная: код просыпается
только когда прилетел апдейт от Telegram. Нет планировщика, нет крона, нет фоновых
джоб. Плюс нет npm-пакетов — значит ни cheerio, ни jsdom, парсинг HTML регулярками
в песочнице. Поллер — это и есть продукт, ему там жить негде. Пересмотреть, если
Telegram завезёт планировщик.

**Не Rails.** Лёгкий долгоживущий процесс. Rails тут экскаватор для клумбы.

**Имя проекта живёт только снаружи.** Репа `kortuli`, бот `@kortuli_bot`, но внутри
нейтральные неймспейсы (`booking`, `slots`, `adapters`) и никаких `KORTULI_` префиксов
в env. Ребрендинг не должен превращаться в sed по всему репозиторию.

## 6. Архитектура

Пять слабо связанных частей:

1. **Adapters** — по одному на клуб, единый интерфейс:
   `fetch(club, date_range) -> [Slot{court_ref, starts_at, ends_at, price, deeplink}]`
2. **Poller** — расписание опроса, per-club интервал + джиттер, backoff на 429/5xx
3. **Differ** — прошлый снапшот vs новый → события `became_available` / `became_taken`
4. **Matcher** — `became_available` × активные вотчеры → кандидаты на уведомление
5. **Notifier** — дедуп, rate limit на пользователя, отправка

Телеграм-слой — тонкий CRUD над вотчерами. Никакой логики в хендлерах команд.

---

## 7. Модель данных (черновик)

- `clubs` — конфиг источника, интервал опроса, состояние здоровья адаптера
- `courts` — корты клуба, с нормализованным идентификатором
- `slots` — текущее состояние + журнал событий (или снапшоты, см. открытые вопросы)
- `watches` — user_id, клубы, дни недели, диапазон времени, активен/нет
- `notifications` — что кому уже отправлено

**Уникальный индекс `notifications (watch_id, court_id, starts_at)` — обязателен.**
Без него на первом же флапе чужого сайта пользователь получит сорок сообщений подряд
и заблокирует бота.

## 8. Нетривиальные места

Сюда смотреть в первую очередь при проектировании — это то, что сломает наивную реализацию.

**a) Идентичность слота.** Многие сайты не отдают стабильных id ни для корта, ни для
слота. Ключ придётся синтезировать из `(club_id, нормализованное имя корта, starts_at)`.
Ломается, когда клуб переименовывает корт. Нужен слой нормализации плюс ручной маппинг
в конфиге клуба.

**b) Скользящее окно бронирования.** Клубы открывают новый день на N дней вперёд,
обычно ночью. Наивный differ увидит разом сотни `became_available` и разошлёт флуд.
Обязательно отличать «слот появился, потому что открылся новый день» от «слот
освободился, потому что отменили». Простейшее решение: не генерировать
`became_available` для дат, которых в прошлом снапшоте не было вообще.

**c) Флапы и ложные срабатывания.** Сайт отдал 500, таймаут или пустой массив — наивно
это выглядит как «все слоты освободились». Нужен guard: если у клуба разом
исчезли или появились *все* слоты, считать это ошибкой опроса, а не событием.

**d) Таймзоны.** Asia/Tbilisi, UTC+4, без перехода на летнее время. Хранить UTC,
показывать локально. Часть сайтов отдаёт локальное время без оффсета — нормализовать
на входе адаптера, а не размазывать конверсию по коду.

**e) Вежливость к источникам.** У клубов шаред-хостинг, а не Amazon. Интервал 3–5 минут
на клуб, джиттер, осмысленный User-Agent с контактом, экспоненциальный backoff. Бан по
IP на второй неделе — совершенно реалистичный сценарий.

**f) Хрупкость адаптеров.** Каждый сломается без предупреждения, когда клуб обновит
сайт. Нужен health-check на адаптер: время последнего успешного опроса, N циклов подряд
с нулём слотов → алерт владельцу бота. Молчащий сломанный адаптер хуже упавшего бота,
потому что незаметен.

## 9. MVP и критерий смерти

**Скоуп:**
- 2 клуба, где реально играешь. Первый — на Reservio.
- Один пользователь — ты.
- Горизонт 7 дней.
- Один сценарий: создать вотчер на окно → получить пуш при отмене.

**Срок:** выходные.

**Критерий смерти:** если через две недели сам не пользуешься — закрывать. Два дня
работы за проверку гипотезы — нормальная цена, а не повод тащить труп дальше.

## 10. Открытые вопросы для фазы архитектуры

- Node или Ruby. Оба в наличии, выбирать по тому, где приятнее писать парсеры и
  держать долгоживущий процесс.
- Postgres или SQLite. SQLite скорее всего хватит, но снапшоты растут — зависит от
  решения ниже.
- Хранить полную историю снапшотов или только текущее состояние + журнал событий.
  Второе компактнее, первое позволяет потом считать аналитику («когда обычно
  освобождаются вечерние слоты») — а это, возможно, будущая фича.
- Ретенция: сколько держать историю.
- UI вотчера: текстовые команды или инлайн-клавиатура. Влияет на то, какие хендлеры
  вообще нужны.
- Верхний предел уведомлений на пользователя в час — чтобы бот не превратился в спамера
  в день массовых отмен.ы
